# 智能诊断与修复

## 四层结构

### 1. 日志解析

`SmapiLogParser` 解析 `SMAPI-latest.txt` / ErrorLogs：

- 头部游戏与 SMAPI 版本
- Loaded mods
- Skipped mods 及原因
- ERROR/ALERT/CRITICAL 行及堆栈
- Content Patcher 错误中的 content pack 名称

失败原因分类：

- 缺失依赖
- API/游戏版本不兼容
- manifest 损坏
- 文件夹结构不完整
- 重复
- 其他运行时错误

原始行和行号保存在 `LogIssue.raw` / `line_number`。

### 2. 静态规则

`StaticRules` 只基于结构化元数据和日志明确文本：

- 必需依赖缺失、版本不足、已禁用
- 重复 UniqueID / 重复安装
- 游戏环境（主程序、Content、Mods、SMAPI、写权限）
- manifest `MinimumApiVersion` 与已安装 SMAPI 版本
- 适配器提供的已知问题规则（默认空，避免编造）

每条规则输出 `DiagnosticFinding`，包含：

- 标题、描述、严重级别
- 确定性：`confirmed` / `known` / `suspected` / `unknown`
- 证据列表
- 建议
- 置信度

**不会因为两个 Mod 出现在同一条日志中就认定冲突。** 冲突措辞只用于：

- 已知问题规则（有公开来源）
- 日志/元数据明确说明的不兼容
- 结构性重复安装（明确事实，不是冲突猜测）

### 3. AI 深度分析

`DiagnosticEngine._analyze_with_ai` 发送：

- 游戏/SMAPI 版本
- 已安装 Mod、依赖状态
- 机器已确认的规则结论
- 日志摘要与截断后的原始日志

提示要求只使用给定证据、返回 JSON、最多 8 条结论。

AI 结果过滤（硬性）：

1. 证据必须能在提供的上下文中找到（归一化空白后子串匹配）；否则整条丢弃。
2. 涉及 Mod 必须存在于当前安装列表；否则移除该 Mod，保留结论。
3. `confirmed` 冲突结论只有在上下文中出现明确“冲突/不兼容”文本时才保留，否则降级为 `suspected`。
4. 置信度上限 0.85。
5. 如果所有结论都被过滤，报告 `ai_error`，不展示编造内容。

AI 只是分析层，不执行修复。

### 4. 诊断报告

持久化到 `diagnostic_runs` / `diagnostic_issues`，UI 显示：

- 问题标题/级别/类别/确定性/置信度
- 涉及 Mod
- 原因与证据
- 原始日志片段
- 推荐解决方案
- 原始日志查看器
- AI 是否参与、模型名称、诊断时间

## 修复计划

`RepairService.create_plan()` 根据诊断结果生成步骤：

| 动作 | 自动 | 说明 |
|---|---|---|
| 禁用重复副本 | 是 | 保留一个，其他只重命名，不删文件 |
| 启用已安装依赖 | 是 | 可逆 |
| 安装缺失依赖 | 条件 | 仅当日志提供明确 Nexus 链接并匹配依赖名 |
| 清理临时文件 | 是 | 仅 ModPilot 下载分片和超过 24h 的安装暂存目录 |
| 安装/更新 SMAPI | 否 | 打开官方页面，用户手动操作 |
| 版本不兼容 | 否 | 提示核对版本，不自动猜版本 |
| 配置/manifest 损坏 | 否 | 建议重新安装，不自动改未知配置 |

执行前：

- UI 必须确认。
- 每个自动步骤再次检查风险。
- 安装依赖前创建/复用安装备份。
- 执行后重新扫描并比较缺失依赖、重复组数量。
- 问题数量增加则自动回滚已执行的启用/禁用和安装备份，并标记计划状态。

手动步骤不会被自动执行；计划中明确显示“需手动操作”。

## 已知问题规则

`modpilot/adapters/stardew/data/known_issues.json` 默认为空。规则结构见 `docs/ADDING_GAME.md`。不要为了“看起来功能完整”添加未经证实的兼容性声明。
